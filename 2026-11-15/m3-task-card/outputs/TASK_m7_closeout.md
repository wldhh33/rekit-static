## 3. 方法问题：校验器与被测模块「同错」是怎么发生的

### 3.1 发生链条（可逐行对照）

1. M6-U1 写实现：`_call_insns` 用 `b.startswith("e8") or b.startswith("ff")` —— **判据是「raw 首字节」**。
2. M6-U1 写校验器：`verify_callgraph.py` 的不变量 B 是「直接调用点集合 == E8 指令集合」，其中 `e8 = {i["addr"] for i in res["instructions"] if i["bytes"].startswith("e8")}` —— **同一判据，重新打了一遍**（代码不共享，语义共享）。
3. 两边取的是**同一份输入** `res["instructions"]`（同一个解码器输出）。
4. 因此该不变量对任何样本都恒真：只要实现漏了某类 E8，校验器的期望集合也同步漏掉同一条，「集合相等」照样成立。M6 的负向基线只锁**计数**（339 / 364 等），不覆盖「指令类别是否枚举完整」。
5. M7-U1 的键覆盖账**另走一条路径**（跳前缀取 opcode），才第一次把这个缺口变成数字（bin_ls 13 / dyn_static 53）。
6. M7-U2 改完实现后，`verify_callgraph.py` **首跑即 FAIL**：`! dyn_static: 直接边 0x4015db 不是 E8 指令`、`直接调用点集合与 E8 指令集合不一致（3457 vs 3456）` —— 这个 FAIL 就是「校验器此前共用同一错误判据」的直接证据。把校验器改为自带 `_opcode()` 后通过。

### 3.2 为什么 M6 当时没发现

- **判据同源**：两边都从「x86 指令字节以 opcode 开头」这一条朴素假设出发。它对无前缀编码成立，对带前缀编码（`41 ff d6`、`43 ff 14 fe`、`67 e8`）不成立。
- **期望值由被测的同一数据源算出**，没有任何外部 oracle（objdump / capstone）参与。
- **不变量形状是「集合相等」**，比较的两端由同一枚举产生；错误在两端同步发生 → 恒真。这类不变量只证明「内部自洽」，不证明「覆盖完整」。

### 3.3 现在有哪些手段（分层，按能否自动化）

**A. 能自动发现：强共享（验收脚本直接 import 被测私有判据来造期望值）**

可用 AST / 正则静态扫描 `tests/verify_*.py`、`tests/test_*.py` 中对 `rekit` 私有符号（`_xxx`）的引用。本轮一次性扫描结果：

| 文件 | 私有符号引用 | 判定 |
|---|---|---|
| `verify_sitejoin.py` | `_decoded_calls` / `_text_lines` / `_slice` / `_is_call_line` / `_KIND_ATTR` / `_slots` | **可接受**：`_decoded_calls` 的结果必须与独立实现的 `_calls_alternate` 相等，二者不等即 FAIL；文本切片类是同层 API 的组成部件 |
| `verify_callfacts.py` | `CG._effects` / `CG._Ctx` / `expr._REG64` | **风险项**：独立复算「基址是否被改写」时复用了实现的效果判定。目前无反向案例，按 R74 列入复检清单，本轮不改代码（避免收口变成新改动单元） |
| `test_expr.py` / `test_recdesc.py` / `test_switchcand.py` | `_next_flags` / `_cond_text` / `_parse_eh_frame` / `_scan_entries` | **可接受**：被测对象本身就是这些内部函数（单元测试直测） |

**B. 能自动发现：有外部 oracle 的判据**

指令类别/长度这类判据有真独立来源：objdump（`verify_disasm.py` 已在用，53/53 对齐）、`expr.decode` 的指令表与 raw 字节模式是两条不同来源。M7-U2 的修法正是把「raw 首字节」换成「跳前缀 opcode + ModRM」，并用 `expr.decode().family` 复核——这一步让实现与判据不再同源。

**C. 不能自动发现：语义重复（两次独立写出同一个错误思路）**

没有静态方法能判定「这两段代码是否表达同一条规则」。只能靠：

1. **独立 oracle 差分**（有外部工具时）；
2. **修正一侧后全量重跑，看校验器是否跟着变**（本轮就是这样暴露的——修正实现 → 校验器 FAIL）；
3. **人工审**。

**结论（直说）**：不存在「全局自动发现同错」的手段。能自动化的只有强共享（A）和有 oracle 的判据（B）；语义重复（C）**只能人工审**，外加「修正后必须重跑 + 前后 diff」这一流程把它逼出来。

### 3.4 已落规则

- **R73**（U2 已落）：校验器不得与被测模块共用同一判据实现；每条「恒成立」不变量至少要有一次注入/反向验证。
- **R74**（本轮新增）：每条硬不变量至少要有**一条独立来源路径**（外部工具或独立重算），且来源必须写进文档；只写「与被测实现一致」不算验收。
- **R75**（本轮新增）：实现侧判据修正后，必须全量重跑所有校验器并做**前后 diff**；校验器 FAIL 优先怀疑校验器同错，不得先改校验器放行。

| M8-U3 | 数据/字符串引用交叉（`.rdata` 字符串 → 引用点 → 所属函数） | **还没做** | 纯机械、可验证、无推断，能直接提升伪 C 可读性 |
| — | 无调试信息时的参数名/类型 | **结构上做不到** | 二进制里不存在该信息；只能给「寄存器/栈槽」事实，不能命名 |
| — | 运行时间接调用目标（虚表、函数指针） | **结构上做不到** | 需执行或符号执行；静态工具包内无判据。要做属另立项目（沙箱/插桩），不能塞进 M8 |
| — | 跨函数精确别名分析 | **结构上做不到** | 无类型与内存布局信息，别名关系不可判定；只能保守 abstain |
| — | 混淆后的控制流还原（flattening 等） | **结构上做不到** | 无 ground truth，无法给出可验证判据；任何结论都不可复核 |

**建议起点**：`M8-U0`（清掉 M7 遗留的两处口径限制）→ `M8-U1`（跨块数据流，判据先行）。不建议直接开 U2：参数绑定没有符号来源时只能产出恒 0 的 `declared` 与大量 abstain，收益低于 U0/U1。

## 8. 能力边界与遗留（不在 M7 修补）

1. `dyn_static` 3 条 `struct_function_absent`：函数未被结构化层覆盖（`function_not_structured`），属口径差异，不是本次能修的下层缺陷；保留单列。
2. `thunk_of` 的「函数体单条指令」限制：见 M8-U0。
3. 序言识别仍是字面模式（`recdesc.PROLOGUE_PATTERNS`）：样本前置前缀命中 0 条，暂无实测影响；扩口径需与 U0 一起做。
4. `verify_callfacts.py` 复用 `CG._effects` / `CG._Ctx` 造期望值（§3.3 表）：已按 R74 列入复检清单，本轮不改代码；若将来 `_effects` 改动，该脚本必须先独立重算再比对。
