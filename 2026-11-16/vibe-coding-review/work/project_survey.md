## 1. 实际工作流（从 M17/M18 任务卡与 PROGRESS 归纳）

一个学习单元的固定动作：

1. **任务卡先行**：`work\outputs\TASK_mNN_<topic>.md`，写目标、非目标、判据、证据要求。
2. **实现**：在 `rekit\` 新增模块（如 `ilflow.py`），CLI 增加子命令，`tests\test_<module>.py` 写单测。
3. **独立验证**：`tests\verify_<module>.py` 用外部工具（objdump/readelf/dncil/官方解析器）重算期望值，再与实现对拍。
4. **全量回归**：`pytest` + 全部既有 verify 脚本，逐条记录 exit code。
5. **收口**：写 `outputs\TASK_mNN_closeout.md`，逐条对账判据；回写 `pack03\PROGRESS.md`（当日行）、`CHANGELOG.md`（条目 + 新规则编号）、必要时 `CHARTER.md`；生成日报 docx。
6. **证据落盘**：`work\evidence_mNN_*.log|json`，失败日志改名保留而不删除。

代表性原文：

- `PROGRESS.md` M7-U1："回归：pytest **382 passed** …… + **11 个验证脚本 exit 0** …… 证据 work/evidence_m7u1_*.log"
- `PROGRESS.md` M7-U2："校验器同错（新发现，审计第 12 项）：`tests/verify_callgraph.py` 与 `tests/test_callgraph.py` 的「直接调用点 == E8 集合」同样按 raw 首字节判定，修正前与被测模块同错、形成自洽假象"
- `TASK_m18_ilflow.md` §1.2："`0 个方法 / 0 个目标（全量）；全部一致` 并判 PASS。**空对空不是通过**，这是本次重写的首要原因。"

## 3. 目录与路径异常（影响可复现）

1. `pack` 下真实目录名：
   - `03_璺\ue21c嚎鍥句笌绔犵▼`（应为 `03_路线图与章程`，含控制字符）
   - `04_rekit椤圭洰婧愮爜`（应为 `04_rekit项目源码`）
   - `05_姣忔棩鏃ュ織`（应为 `05_每日日志`）
   - `06_鏃ユ姤docx`（应为 `06_日报docx`）
   典型 GBK/UTF-8 混淆。Python 以 UTF-8 读取文件名时直接看到 mojibake，说明磁盘名本身就是坏的，不是终端显示问题。
2. `pack` 缺 `01_方法论文档`、`02_规则库`；这两册只在 `tmp\pack` 中存在（且 `tmp\pack` 的代码是 5 模块 M1.5 快照）。
3. `pack\README.md` 仅 2,691 字节，仍写"73 断言"，与当前 25 模块/554 测试的规模严重脱节。
4. `work\rekit`、`work\tests` 是指向 `pack` 的目录联接（junction）；`work\samples` 是物理目录。这意味着"复制 work 目录"并不复制代码，但会复制 99 MB 样本。

## 6. 已观察到的流程成本

- **收口成本**：一次收口要写 PROGRESS + CHANGELOG + 任务卡对账 + 日报，数字从多处手抄。
- **入口成本**：21 条验证命令，9 个脚本无参数、12 个参数不一，其中 `verify_fingerprint` 需要 `--all --matrix` 特殊组合。
- **上下文成本**：PROGRESS 103 KB、CHANGELOG 69 KB，单会话无法全量加载；M18 已因此中断。
- **副本成本**：三处源码/样本目录，无归档标注；`tmp` 副本会误导读者。
